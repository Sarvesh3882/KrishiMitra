# KrishiMitra — Blackout Challenge Demo Guide

> For hackathon judges and team members.
> Run the backend first: `uvicorn main:app --host 127.0.0.1 --port 8000 --reload`

---

## 1. What is an Operation ID?

Every important farmer action — posting a produce listing, saving a local need,
updating a profile — is assigned a **unique Operation ID** before it is sent to
the database.

Example:
```
OP-DEMO-001
OP-M0JX2K4F-A3Z9Q1     ← real IDs generated by the frontend
```

The ID is generated **on the client device**, stored locally, and sent with the
request to the backend.

---

## 2. Why does it exist?

The Operation ID solves two problems:

| Problem | Without Op ID | With Op ID |
|---------|--------------|------------|
| Database temporarily down | User's action is silently lost | Operation stays on device, retry later |
| User taps "Submit" twice | Two duplicate records in DB | Second request detected and rejected |

The ID is the **identity of the action**, independent of whether the database
write succeeded.

---

## 3. What happens if the database write fails?

```
FARMER taps "Post Listing"
        │
        ▼
Frontend generates OP-DEMO-001
        │
        ▼
Saved to IndexedDB (local browser storage)   ← NEVER LOST
        │
        ▼
POST /api/v1/writes/produce_listing  →  Database DOWN
        │
        ▼
Backend marks OP-DEMO-001 as DATABASE_UNAVAILABLE
        │
        ▼
Frontend keeps OP-DEMO-001 in its pending queue
        │
        ▼
Farmer sees: "Will retry when connection returns"
```

The action is **not lost**. It waits in the queue.

---

## 4. How is the operation retried?

When the database comes back online:

```
Frontend detects connection restored
        │
        ▼
Resends POST /api/v1/writes/produce_listing
with the SAME OP-DEMO-001
        │
        ▼
Backend checks write_operations table
        │
        ▼
OP-DEMO-001 exists and is still PENDING → proceed with write
        │
        ▼
Database write succeeds
        │
        ▼
OP-DEMO-001 marked COMPLETED
        │
        ▼
Frontend removes OP-DEMO-001 from local queue
```

---

## 5. How are duplicates prevented?

The `write_operations` database table has a **UNIQUE constraint** on `operation_id`.

If the same request arrives twice:

```sql
-- First arrival: OP-DEMO-001 inserted as pending → OK
-- Second arrival: INSERT fails with UNIQUE violation

→ Backend catches this
→ Returns the previous COMPLETED result
→ No second produce listing is created
```

This is called **idempotency** — the same operation can be retried any number
of times and will only ever produce **one** result.

## 6. How to run the 3 demo operations

Make sure the backend is running:
```bash
cd backend
uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

### Step 1 — View all demo operations
```
GET http://localhost:8000/api/demo/operations
```

### Step 2 — Process OP-DEMO-001 (normal success path)
```
POST http://localhost:8000/api/demo/operations/OP-DEMO-001/process
Body: {}
```
Watch the server console — you will see:
```
[OPERATION]   OP-DEMO-001  →  Farmer lists Onion for sale
[TYPE]        OP-DEMO-001  →  PRODUCE_LISTING
[STATUS]      OP-DEMO-001  →  PROCESSING
[IDEMPOTENCY] OP-DEMO-001  →  CHECK — inspecting write_operations table
[DATABASE]    OP-DEMO-001  →  WRITE ATTEMPT
[DATABASE]    OP-DEMO-001  →  WRITE SUCCESS — id=<uuid>
[OPERATION]   OP-DEMO-001  →  OP-DEMO-001 COMPLETED
```

### Step 3 — Process OP-DEMO-002 with simulated failure
```
POST http://localhost:8000/api/demo/operations/OP-DEMO-002/process
Body: { "simulate_db_failure": true }
```
Console shows:
```
[DATABASE]    OP-DEMO-002  →  UNAVAILABLE — simulated failure
[OPERATION]   OP-DEMO-002  →  OP-DEMO-002 PRESERVED — retained for retry
```

### Step 4 — Retry OP-DEMO-002
```
POST http://localhost:8000/api/demo/operations/OP-DEMO-002/retry
```
Console shows:
```
[RECOVERY]    OP-DEMO-002  →  RETRYING OP-DEMO-002
[OPERATION ID] OP-DEMO-002 →  SAME ID REUSED — not regenerated
[IDEMPOTENCY] OP-DEMO-002  →  CHECK — will not duplicate if already done
[DATABASE]    OP-DEMO-002  →  WRITE SUCCESS
[OPERATION]   OP-DEMO-002  →  OP-DEMO-002 COMPLETED
```

### Step 5 — Retry OP-DEMO-002 AGAIN (demonstrate no duplicate)
```
POST http://localhost:8000/api/demo/operations/OP-DEMO-002/retry
```
Console shows:
```
[IDEMPOTENCY] OP-DEMO-002  →  ALREADY COMPLETED — result_reference=<uuid>
[IDEMPOTENCY] OP-DEMO-002  →  NO DUPLICATE CREATED — returning previous result
```
Response:
```json
{ "status": "COMPLETED", "replayed": true, "message": "Idempotency: operation already completed — no duplicate created" }
```

### Reset for re-demonstration
```
POST http://localhost:8000/api/demo/reset
```
This resets in-memory status back to PENDING without deleting DB records.

## 7. API Endpoints for the Demo

| Method | URL | Purpose |
|--------|-----|---------|
| GET  | `/api/demo/operations` | List all 3 demo operations + current status |
| GET  | `/api/demo/operations/{id}` | Full detail for one operation |
| POST | `/api/demo/operations/{id}/process` | Process an operation (optionally simulate failure) |
| POST | `/api/demo/operations/{id}/retry` | Idempotent retry |
| POST | `/api/demo/reset` | Reset demo to initial state |
| GET  | `/api/resilience/status` | Live database connectivity + feature flags |
| GET  | `/api/resilience/operations` | All real write_operations records |

## 8. Key points to explain to judges

> "Our primary store is Supabase PostgreSQL — we don't assume every write succeeds.
>
> Before an important farmer action leaves the device, we assign it an Operation ID
> and retain it in an IndexedDB pending queue.
>
> The backend processes the operation transactionally and uses the Operation ID as an
> idempotency key. If the database fails mid-write, the operation is retained and
> retried with the **same ID** — not a new one — so no duplicates are created.
>
> For actual database corruption, PostgreSQL backups provide the recovery point.
>
> We handle two different failure windows:
> 1. In-flight failure → pending queue + retry + idempotency
> 2. Database loss → backup + restore"
